= Federated agent search across {registry} instances

:_mod-docs-content-type: ASSEMBLY

[role="_abstract"]
With federated agent search, one {registry} instance searches the Agent Cards it stores and those of other {registry} instances, its peer registries, in a single request. Each agent in the response says which registry it came from, and each registry has an outcome of its own, so a slow or failing peer does not fail the search.

== How federated agent search works

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
A federated search runs the agent search of this registry and calls the agent search of every enabled peer registry in parallel, all under one deadline.

Public agents only:: Peers are called anonymously and asked for `public` Agent Cards only. A peer returns an Agent Card only when it carries the `apicurio.agent.visibility=public` label, whatever the peer's own authentication settings. A peer must confirm in its answer that it applied the public-only mode. An answer without that confirmation, for example from an older registry that ignores the request, is discarded and the peer is reported as `unsupported`. For the visibility labels, see xref:getting-started/assembly-a2a-features.adoc#a2a-visibility-model_{context}[Agent visibility model].
No caller credentials are forwarded:: The caller's credentials are never sent to a peer. A peer is called anonymously, unless peer credentials are enabled and the peer has a credential reference, in which case it is called with its own configured credential. See xref:getting-started/assembly-federated-agent-search.adoc#searching-peers-with-credentials_{context}[Searching a peer with a credential].
This registry's own results:: The caller's own visibility rules apply to the results of this registry, exactly as for `/.well-known/agents`.
One hop only:: Every call to a peer carries an `X-Federation-Hop` header, and a registry refuses a federated search that carries one. A search is therefore forwarded at most once, and two registries that list each other as peers do not loop.
Source attribution:: Every agent in the response has a `source`: `local` for this registry, or the peer it came from. Agents with the same group and artifact ID from different sources are all returned, since nothing proves that two registries publish under the same identity.
Peer details for administrators only:: The list of peers is for administrators, so only a caller who may list the peers sees the peer ids and the reason a peer failed: an administrator, by role or by admin override, or anyone when authentication is off. Any other caller, anonymous callers included, sees each peer as `peer-1`, `peer-2` and so on, numbered in peer id order within the one response, with its outcome but without a reason.
Peer data is not checked:: Apart from `source`, every field of an agent from a peer is what the peer returned. The `owner` of an agent from a peer is left out, since it names a principal of another registry.

== Enabling federated agent search

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Federated agent search is an experimental feature and is disabled by default.

.Prerequisites
* A2A support is enabled on every registry that takes part, including the peers. A peer that does not serve `/.well-known/agents` is reported as `unsupported`.

.Procedure
. Enable experimental features, A2A and federation on the registry that runs the federated search:
+
[source,bash]
----
APICURIO_FEATURES_EXPERIMENTAL_ENABLED=true
APICURIO_A2A_ENABLED=true
APICURIO_FEDERATION_ENABLED=true
----
. Optional: to show the *Agents* page and the *Include remote registries* switch in the {registry} web console, also set `APICURIO_UI_FEATURES_AGENTS_ENABLED=true`.
. Optional, for development and testing only: allow peers over plain HTTP, or on loopback addresses:
+
[source,bash]
----
APICURIO_FEDERATION_PEER_INSECURE_HTTP_ENABLED=true
APICURIO_FEDERATION_PEER_LOOPBACK_ENABLED=true
----
+
Both settings apply to every peer, including peers loaded from GitOps or KubernetesOps storage.

.Verification
* `GET /apis/registry/v3/search/federated` returns `200`. While federation is disabled, it returns `409`.

== Managing peer registries

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Peer registries are managed through the admin REST API, which requires the admin role when authorization is enabled. In GitOps and KubernetesOps storage, peers are declared in the `peers` list of the `registry-v0` file instead, and the full list is replaced on every load.

.Procedure
. Register a peer:
+
[source,bash]
----
curl -X POST http://localhost:8080/apis/registry/v3/admin/peers \
  -H 'Content-Type: application/json' \
  -d '{"peerId": "eu-west", "url": "https://registry.eu.example.com", "name": "EU registry"}'
----
+
`peerId` and `url` are required. The `peerId` uses lowercase letters, digits, `.`, `_` and `-`, and `local` is reserved. A peer is enabled unless you send `"enabled": false`.
. List the peers with `GET /apis/registry/v3/admin/peers`, update one with `PUT /apis/registry/v3/admin/peers/\{peerId}`, and remove one with `DELETE /apis/registry/v3/admin/peers/\{peerId}`.

In the web console, an admin can do the same on the *Remote registries* tab.

In GitOps or KubernetesOps storage, declare the peers in the `registry-v0` file of the registry:

[source,yaml]
----
$type: registry-v0
registryId: prod
peers:
  - peerId: eu-west
    url: https://registry.eu.example.com
    name: EU registry
    enabled: true
----

The peer URL must use `https`, unless plain HTTP is allowed, and must be an absolute URL with a host. A host that is, or resolves to, a loopback, link-local, unspecified, multicast, reserved or cloud metadata address is refused. Loopback addresses can be allowed for testing. The host name is resolved when the peer is called, every address it resolves to is checked, and the connection goes to the checked addresses in the order they were resolved, moving on when one cannot be connected to. The certificate is still verified against the host name.

At most `apicurio.federation.search.max-peers` peers can be enabled through the admin API. If more are enabled anyway, for example after the setting was lowered or through GitOps or KubernetesOps storage, a search queries the first ones in peer id order and reports the rest as `failed` with the reason `capacity_exceeded`.

The `credentialSecretRef` field names the credential of a peer. It is used only when peer credentials are enabled, as described in the next section.

[id="searching-peers-with-credentials_{context}"]
== Searching a peer with a credential

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
When a peer only answers authenticated requests, for example because it sits behind an authenticating gateway, this registry can call it with a credential of its own. The search still asks the peer for `public` Agent Cards only, so a credential never widens what a peer returns, even when it belongs to an account that can read more.

.Procedure
. Put each credential, a bearer token, in its own file in one directory, named after the key that the peer will reference. Only the token goes in the file. A trailing line break is ignored.
. Set the directory on the registry that runs the federated search:
+
[source,bash]
----
APICURIO_FEDERATION_PEER_CREDENTIALS_DIR=/etc/apicurio/peer-credentials
----
+
The registry does not start if the directory does not exist. While the property is not set, every peer is called anonymously, whether or not it has a credential reference.
. Set `credentialSecretRef` on the peer to the name of its file:
+
[source,bash]
----
curl -X PUT http://localhost:8080/apis/registry/v3/admin/peers/eu-west \
  -H 'Content-Type: application/json' \
  -d '{"url": "https://registry.eu.example.com", "enabled": true, "credentialSecretRef": "eu-west-token"}'
----

On Kubernetes, mount one Secret as the credentials directory, as a whole volume and without `subPath`, so that keys added or rotated in the Secret reach the registry without a restart:

[source,yaml]
----
volumes:
  - name: peer-credentials
    secret:
      secretName: registry-peer-credentials
containers:
  - name: registry
    env:
      - name: APICURIO_FEDERATION_PEER_CREDENTIALS_DIR
        value: /etc/apicurio/peer-credentials
    volumeMounts:
      - name: peer-credentials
        mountPath: /etc/apicurio/peer-credentials
        readOnly: true
----

The credential is read again for every call, so a replaced token is used from the next search. The file can be a symbolic link, as the keys of a Secret volume are, but it must resolve to a place inside the credentials directory. A credential that is missing, unreadable, empty, larger than 16 KiB, or not a valid bearer token makes the peer fail with the reason `credential_unavailable`, and the peer is not called anonymously instead. A credential the peer rejects makes it fail with `unauthorized`.

The credential is sent only to the peer's own address, since redirects are not followed. It never appears in the peer API, in search responses or in logs. Use `https` peer URLs for credentialed peers; plain HTTP sends the token unencrypted.

== Searching agents across registries

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
The federated search takes the same filters as the agent search of `/.well-known/agents`. When authorization is enabled, the caller needs read access.

.Procedure
* Search for agents with a skill, across this registry and its peers:
+
[source,bash]
----
curl 'http://localhost:8080/apis/registry/v3/search/federated?skill=translate&perSourceLimit=10'
----
+
The query parameters are `name`, `skill`, `capability`, `inputMode` and `outputMode`. Repeat `skill`, `capability`, `inputMode` and `outputMode` to require several values. `perSourceLimit` is the maximum number of agents from each source. It defaults to `20`. A value below `1` is refused with `400`, and a value above `apicurio.federation.search.per-source-limit.max` is lowered to it. There is no paging across sources.

Each search calls every enabled peer once, so one request leads to as many outbound calls as there are enabled peers. One caller can have at most `apicurio.federation.search.max-searches-per-caller` searches in progress at once. A search beyond that still returns this registry's results, but calls no peer and reports every peer as `capacity_exceeded`. Authenticated callers are told apart by principal name and anonymous callers by network address, so behind a proxy that does not forward the client address, all anonymous callers share one limit.

.Example response
[source,json]
----
{
  "agents": [
    { "source": "local", "groupId": "demo", "artifactId": "local-helper", "name": "local-helper" },
    { "source": "eu-west", "groupId": "demo", "artifactId": "remote-translator", "name": "remote-translator" }
  ],
  "sources": [
    { "source": "local", "outcome": "ok", "count": 1, "truncated": false },
    { "source": "eu-west", "outcome": "ok", "count": 1, "truncated": false },
    { "source": "gone", "outcome": "failed", "reason": "unreachable", "count": 0, "truncated": false }
  ]
}
----

The example is what an administrator sees. Another caller sees `peer-1` for `eu-west` and `peer-2` for `gone`, and no `reason`.

In the web console, open the *Agents* page and turn on *Include remote registries*. Each agent shows the registry it came from, and a row of labels shows the outcome of every registry. Agents from a peer open on their own registry, not in this one.

[id="federation-outcomes_{context}"]
== Source outcomes and failure reasons

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The response is `200` whenever the search of this registry succeeds, even when some or all peers fail. Each entry in `sources` has one of the following outcomes.

.Source outcomes
[cols="1,3",options="header"]
|===
|Outcome |Meaning
|`ok` |The source answered and its agents are in the response. `truncated` is `true` when more agents matched than `perSourceLimit`.
|`deadline_exceeded` |The search ran out of time before the peer answered. This says nothing about the peer's health.
|`unsupported` |The peer did not confirm the public-only mode, or has no agent search, so its answer was discarded.
|`failed` |The source could not be searched. For a caller who may list the peers, `reason` says why.
|===

.Failure reasons
[cols="1,3",options="header"]
|===
|Reason |Meaning
|`unauthorized` |The peer answered `401` or `403`.
|`unreachable` |The peer could not be reached, or its address is not allowed.
|`timeout` |The peer did not answer within the per-peer timeout.
|`peer_error` |The peer answered with a server error, or with a redirect. Redirects are not followed.
|`invalid_response` |The peer's answer was malformed, too large or inconsistent.
|`circuit_open` |The peer has been failing repeatedly and was not called.
|`credential_unavailable` |The peer has a credential reference and peer credentials are enabled, but the credential could not be read or is not a valid bearer token. The peer was not called.
|`capacity_exceeded` |The peer was not called: too many peer calls were in progress across all searches, too many name lookups for this peer were in progress, the caller had too many searches in progress, or more peers are enabled than one search queries.
|===

The federated search itself fails in the following cases:

* `400`: the request carries an `X-Federation-Hop` header, because another registry forwarded it, or `perSourceLimit` is below `1`.
* `404`: A2A support is not enabled.
* `409`: federation is not enabled.
* `503`: the search of this registry did not finish before the deadline. The calls to the peers are cancelled.

== Federation configuration properties

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The following properties bound the time, the number of calls and the size of the answers of a federated search.

.Federation configuration properties
[cols="2,1,3",options="header"]
|===
|Property |Default |Description
|`apicurio.federation.enabled` |`false` |Enables the peers API and federated agent search. Requires `apicurio.features.experimental.enabled=true`.
|`apicurio.federation.search.deadline-ms` |`5000` |Time limit for the whole federated search, including this registry's own search.
|`apicurio.federation.search.peer-timeout-ms` |`3000` |Time limit for one call to a peer.
|`apicurio.federation.search.max-peers` |`16` |Maximum number of peers a federated search queries, and that can be enabled through the admin API.
|`apicurio.federation.search.max-concurrent-calls` |`64` |Maximum number of peer calls in progress at once, across all federated searches, from the name lookup until the answer has been read or the call cancelled.
|`apicurio.federation.search.max-searches-per-caller` |`2` |Maximum number of federated searches one caller can have in progress at once.
|`apicurio.federation.search.max-response-bytes` |`1048576` |Maximum size of the answer accepted from one peer. Text fields from a peer have no other bound.
|`apicurio.federation.search.per-source-limit.max` |`100` |Upper bound for `perSourceLimit`.
|`apicurio.federation.search.breaker.request-volume-threshold` |`4` |Number of recent calls to a peer that must have been made before its circuit breaker can open.
|`apicurio.federation.search.breaker.failure-ratio` |`0.5` |Share of failed calls among the recent calls that opens the circuit breaker of a peer.
|`apicurio.federation.search.breaker.delay-ms` |`30000` |Time a peer's circuit stays open before the peer is called again.
|`apicurio.federation.peer.insecure-http.enabled` |`false` |Allows peer URLs that use plain HTTP. For development and testing only.
|`apicurio.federation.peer.loopback.enabled` |`false` |Allows peers on loopback addresses. For development and testing only.
|`apicurio.federation.peer.credentials.dir` |None |Directory of peer credentials. When set, a peer with a `credentialSecretRef` is called with the content of that file as a bearer token. When not set, every peer is called anonymously.
|===

When federation is enabled, these settings are checked at startup, and the registry does not start if one is out of range. `peer-timeout-ms` must be below `deadline-ms`, every time and limit must be at least `1`, `breaker.failure-ratio` must be above `0` and at most `1`, `breaker.delay-ms` must not be negative, and `peer.credentials.dir`, if set, must be an existing directory.

Each peer has its own circuit breaker, so a peer that keeps failing is skipped without any effect on the others. Only transport failures, server errors and timeouts count against a peer. A `401` or `403`, an unsupported peer, a malformed answer, a refused address, a call cancelled at the deadline, a call this registry had no capacity for and a credential that could not be read do not.

The service records the metrics `apicurio.federation.peer.search`, a timer tagged by `peer`, `outcome` and `reason`, and `apicurio.federation.peer.circuit.state`, a gauge per peer that is `0` when its circuit is closed, `1` when half open and `2` when open. The metrics use the real peer ids, whoever searched. The meters of a peer are removed once it is no longer enabled.
